# 操作マニュアル

画面ごとの詳細リファレンスです。導入方法は[インストールマニュアル](installation.ja.md)、初めての方向けの流れは[はじめての方向けガイド](getting-started.ja.md)を参照してください。

## ログイン

個人ごとのアカウントではなく、`ADMIN_USERNAME`（既定値`admin`）/ `ADMIN_PASSWORD`環境変数で設定した**共有アカウントが1つだけ**存在します。セッションやトークンは無く、ブラウザがこのユーザー名/パスワードをHTTP Basic認証として毎リクエスト送信します（この情報はブラウザの`localStorage`に保存されます）。明確な「ログアウト」機能はありません。ブラウザのサイトデータを消すか、（パスワードを間違えるなどで）401エラーになるとログイン画面に戻ります。

「Googleでログイン」「GitHubでログイン」ボタンは表示されますが無効化されています。OAuth連携は実装されていないため、動作を期待しないでください。

## ダッシュボード

作品をカード形式で一覧表示し、それぞれジャンルと記事数を表示します。右側のパネルには、最も新しく作成された作品について、話数・未解決の連続性課題数・作品健全性スコアなどの詳細統計が表示されます。カードをクリックするとその作品を開きます。「＋ 新規作品作成」から新規作成フォームが開きます。

※初期の設計スケッチにあった「AI利用状況」（トークン使用量など）の統計は未実装です。現時点では利用状況を記録する仕組みはありません。

## 作品作成

入力項目：作品名（必須）、ジャンル、あらすじ、自由記述の「詳細設定」（文体・想定読者・外せない制約などAIに常に守らせたい内容）。いずれも`Project`データにそのまま保存され、後から「設定」画面で編集できます。

## 作品ホーム

作品を開いたときに最初に表示される画面です。作品名・ジャンル・あらすじ・進捗を表示するヘッダー、他の全画面への3×3のアイコングリッド、話数が大きい順に上位5件を表示する「最近の更新」リストがあります。

## テキストファイルからのインポート

「なろう」形式（【】で区切られたセクション）のプレーンテキストファイルから、2通りの方法で取り込めます。

- **ダッシュボード →「ファイルからインポート」**：メタ情報（タイトル・あらすじ・ジャンル）付きの本編ファイル（`------- エピソードN開始 -------`区切り）から、新しい作品を作成します。解析されたタイトル・あらすじ・ジャンルが新規作品のフィールドになり、全エピソードが登録されます。
- **既存作品を開いて、設定 →「インポート」タブ**：同じ本編形式、またはメタ情報のない下書きエピソードファイル（`-------第N話「タイトル」-------`区切り。タイトルは区切り行自体に含まれる）から、その作品にエピソードを追加・更新します。既存の話数は本文が上書きされます（上書き前の内容はその話の改訂履歴に自動保存されます）。新しい話数は新規作成されます。

いずれもバックグラウンドジョブとして実行され、進捗を確認できます（`GET /api/v1/import-jobs/{id}`を2秒ごとにポーリング）。1回のリクエストで完結させず、話ごとに実際のAI処理（RAGの再索引付け、通常保存時と同じキャラクター状態抽出、そして全話取り込み後に1回の作品全体の連続性監査）が走るためです。話数が多いと数分かかることがあります。進捗バーは「処理済み話数 / 総話数」を表示し、ダイアログを閉じてもジョブ自体はキャンセルされません（ダッシュボードのインポートはバックグラウンドで継続、設定タブのインポートはそのタブを開いている間ポーリングを続けます）。インポート開始時にも[デスクトップ通知の許可](#自動執筆)を求め、ジョブ終了時に通知します——自動執筆と同じ注意点（このタブを開いている間だけ動作。プッシュ通知ではない）が当てはまります。

どちらの形式かはパーサーが自動判定するため、モードを選ぶ必要はありません。どちらの形式にも一致しないファイル（認識可能なエピソード区切りがない）は、ジョブを作成する前に400エラーで拒否されます。

## 執筆

執筆の中心となる3カラム画面です。

- **左**：この作品のエピソード一覧と、次のエピソードを自動採番で追加する「＋ 新規エピソード」。
- **中央**：選択中エピソードのタイトル・一行概要・本文入力欄。「保存＋人物状態更新」を押すと、本文の保存、意味検索用の再索引付け、AIによる本文からのキャラクター状態変化の抽出が行われます。これらの裏側の処理（OllamaやQdrantへの接続を含む）が失敗した場合は、エディタ上部に警告バナーが表示されます（黙って失敗することはありません）。
- **右（AI EDITOR-IN-CHIEF）**：Context Builderに基づくAIアシスタントです。「⚠ 連続性を監査」は、この作品に登録された全設定と本文の矛盾をチェックします。4つの主要アクション（続きを書く／次の展開／要約／校正）と6つの「QUICK CUSTOM CHECKS」ボタンは、いずれも現在のストーリー情報を添えてAIにプロンプトを送信し、結果はAI RESULT欄に表示されます。「＋ 本文に追加」で結果を本文末尾に追記できます。
- **エディタツールバー**：B／I／H／❝ボタンは、選択中のテキスト（またはカーソル位置）をMarkdown記法（`**強調**`、`*斜体*`、`## 見出し`、`> 引用`）で囲む/挿入するだけで、実際のリッチテキスト書式にはなりません（保存される本文は常にプレーンなMarkdownテキストです）。「プレビュー」でそのMarkdownをHTMLとして表示確認でき、「編集に戻る」で編集画面に戻ります。ツールバー横には（空白を除いた）文字数がリアルタイムで表示されます。
- **🕘 履歴（変更履歴）**：以前と異なる内容で保存するたびに、直前の版がスナップショットとして保存されます（1エピソードあたり最大20件）。このボタンで一覧表示し、「この版に復元」で復元できます。復元操作自体も、復元前の内容をスナップショットするため取り消し可能です。

## プロット／キャラクター／世界観／年表／伏線／用語集

これら6画面は、フィールド構成だけが異なる同一の「一覧＋フォーム（作成・編集・削除）」UIを共有しています。

| 画面 | 項目 |
|---|---|
| プロット | タイトル、種類、状態、開始/終了話数、目的、対立、決着 |
| キャラクター | 名前、役割、性格、口調、目標、状態（alive/dead/missing/unknown）、補足 |
| 世界観 | 名称、種類、説明、ルール、場所、時代 |
| 年表 | 話数、出来事、世界内時間、説明 |
| 伏線 | タイトル、説明、設置/回収話数、状態（open/resolved/abandoned） |
| 用語集 | 用語（名称）、説明、カテゴリ（場所欄を使用） |

**用語集は独立したデータ種別ではありません。** `entity_type: "glossary"`を持つ世界観データとして保存され、クライアント側でフィルタ表示しているだけです。世界観画面には`glossary`タグの付いたものは表示されないため、2つの一覧は重複しません。これによりバックエンドの構成をシンプルに保っていますが、実装としては少し間接的です。APIを直接叩く場合（`GET /api/v1/projects/{id}/world`）には用語集の項目も混在して返ってきます。

ここに登録した内容はすべて、本文生成時・連続性チェック時にAIのコンテキストとして渡されます。これが、長編作品の一貫性を保つための仕組みです。

## 分析ダッシュボード

「Story Digital Twin」（`GET /api/v1/projects/{id}/story-twin`）を基にしたタブ形式のダッシュボードです。

- **概要**：話数・キャラクター数・世界観数・プロット数・伏線数、健全性スコア、本文カバレッジ（本文が入力済みのエピソードの割合）、アクティブなプロット、未回収の伏線。
- **人物関係図／世界観グラフ／時系列グラフ**：関係グラフ。キャラクター/世界観のエッジは、明示的に登録した関係に加えて「同一エピソードでの共起」による推定（2人のキャラクターが同じ話の本文に登場すると弱い自動リンクが付く）も含みます。薄く表示される自動推定エッジを過度に信用しないでください。
- **状態履歴**：各エピソード保存後にAIが抽出した、直近のキャラクター状態のスナップショット。
- **文字数**：総文字数・平均文字数（空白を除く）と、話数順の累積文字数グラフ。執筆ペースの目安ですが、時系列（いつ書いたか）ではなく話数の並び順に基づく点に注意してください。
- **連続性**：執筆画面と同じ連続性監査を、作品全体を対象に実行・確認できます。

健全性スコアはヒューリスティック（連続性課題数＋本文カバレッジから算出）であり、文章の質を測るものではありません。

## 検索

Qdrantによる本文のセマンティック検索です。Qdrantに接続できない場合は、単純なPostgreSQLの部分一致検索（`ILIKE`）へ自動的に切り替わります。画面上に、実際にどちらが結果を返したか（「セマンティック検索 (Qdrant)」／「全文一致 (PostgreSQL フォールバック)」）が表示されます。「再構築」でこの作品の全エピソードを再索引します（このボタンは現在の作品を検索対象にしている場合のみ表示されます）。

「すべての作品を検索対象にする」にチェックすると、`POST /api/v1/rag/search-all`を使って全作品のエピソードを横断的に検索します。各結果にはどの作品由来かが表示されます。このモードには「再構築」ボタンはありません（索引の再構築は各作品の検索画面から行ってください）。

### 検索・全置換

同じ画面の「検索・全置換」タブは、セマンティック検索とは別の、現在の作品のエピソードを対象にしたプレーンテキストの検索・置換機能です（`GET`/`POST /api/v1/projects/{id}/text-search`・`/text-replace`）。検索文字列と置換後の文字列を入力し、大文字小文字の区別をトグルして検索すると、一致した各エピソードがヒット件数と前後のスニペット付きで一覧表示され、置換対象として初期選択されます（不要なものはチェックを外せます）。置換はチェックの入ったエピソードのみに適用され、各エピソードの置換前の内容は改訂履歴に自動保存されるため、置換後もエピソードごとに元に戻せます。

## AIチャット

執筆画面のアシスタントと同じストーリー情報を使った自由対話です。会話履歴は**作品ごとにサーバーに保存**されます（`GET`/`POST`/`DELETE /api/v1/projects/{id}/chat`）。この画面に戻ったときやページを再読み込みしたときも表示されます。「履歴を削除」でその作品の履歴を完全に削除できます。AIの返答は執筆画面のプレビューと同様にMarkdown（見出し・太字・表・罫線）としてレンダリングされます（`##`や`**`、`|`などの記法がそのまま文字として表示されることはありません）。

## 自動執筆

階層的な計画パイプラインを用いて、指定した範囲（1〜最大500話）のエピソードを人手を最小限にして生成します。

```
Series Planner   （1〜500話全体の構成）
  → Arc Planner       （100話単位×5アーク）
    → Mini Arc Planner （各アーク内、10話単位×10ミニアーク）
      → Episode Planner （話ごとの執筆計画）
        → Writer         （本文を実際に生成）
        → Controller監査  （時系列・人物・世界観・プロットをチェック。必要なら再執筆を強制）
```

2つのモデルの役割があります（設定方法は[動作要件](requirements.ja.md)参照）。

- **Writer** — 本文を生成します。既定値`qwen3.8:27b`、ジョブごとに上書き可能。
- **Controller** — 上記の計画立案の全階層と、執筆前後の品質チェック（時系列・人物状態・世界観・プロットの整合性のみを担当し、文章表現の巧拙は判定しません）を行います。既定値`qwen3:14b`、ジョブごとに上書き可能。

ジョブの開始：開始/終了話数、任意の自由記述「追加方針」（追加の指示）、既存エピソードを上書きするかどうか（既定はオフ＝本文が既にあるエピソードはスキップ）を指定します。計画（Series/Arc/Mini Arcレベル）は一度だけ生成され、指定範囲内のエピソード全体で再利用されます。必要な範囲だけ遅延的に展開されます。

進捗表示：パーセンテージ、フェーズラベル（queued／series_planner／arc_planner／controller_preflight／writer／controller_gate／completed／stopped／error）、Arc/Mini Arc/Episode Planの策定数と、実際に本文が書かれた話数を表示します。ジョブ実行中はServer-Sent Events（`GET /api/v1/auto-write/{id}/stream`）でリアルタイムに更新されます。「■ 停止する」は穏やかな停止要求で、実行中の話の生成を完了させてから停止します（生成途中で強制終了はしません）。下部の履歴リストには作品の直近のジョブが表示され、完了後もクリックして内容を確認できます。

5話生成するごとに、連続性の全体監査も自動的に実行されます。

「▶ 自動執筆を開始」を押すと、ブラウザの通知許可も求められます（未決定の場合のみ）。許可すると、ジョブが終了した瞬間（完了・停止・エラーいずれも）にデスクトップ通知が届くため、進捗バーを見続ける必要がありません。このタブを開いたままにしている間だけ動作します。プッシュ通知ではなく通常のブラウザ`Notification`のため、タブやブラウザを閉じていると届きません。[ファイルインポート](#テキストファイルからのインポート)のジョブも同様に動作します。

## 設定

- **基本設定**：作品名・ジャンル・あらすじ・作品ルール・目標話数を編集し、APIを通じて即時保存します。
- **AI設定**：**このブラウザ**における、自動執筆開始フォームの初期値となるWriter/Controllerモデル名を設定します。
- **接続設定**：QdrantのURL、Ollama1（Writer）・Ollama2（Controller）両方のURL/モデル名をこの画面から変更でき、保存すると再起動なしで即座に反映されます。詳しくは下記「[接続設定](#接続設定-1)」を参照してください。SQL（データベース本体）はマスク表示のみの読み取り専用です。
- **エクスポート**：全エピソードの本文（タイトル・概要・本文のみ。キャラクター/世界観/プロット/伏線などの設定データは含みません）を1ファイルにまとめて書き出します。テキスト（.txt）、Markdown（.md）、どのe-readerでも開ける最小構成の有効なEPUB3（.epub）から選べます。`GET /api/v1/projects/{id}/export?format=txt|md|epub`。

### 接続設定

`GET`/`PUT /api/v1/system-settings`。Qdrant URL、Ollama1（Writer）のURL/モデル/埋め込みモデル、Ollama2（Controller）のURL/モデルを、それぞれこの画面から上書きできます。現在サーバーの環境変数の既定値ではなく上書き中の項目には「（上書き中）」と表示されます。空欄で保存するとその項目は既定値に戻ります。これらの上書き値はデータベースに保存され、次回のAI/検索呼び出しから即座に反映されます（QdrantとOllamaのクライアントは呼び出しごとに新規生成されるため、再起動は不要です）。

データベース接続先（`DATABASE_URL`）はこの画面からは意図的に変更できません。稼働中のアプリが、まさにこの設定画面を読み込むために使っている接続をリクエストの途中で切り替えるのは安全ではないためです。変更する場合は環境変数`DATABASE_URL`を編集してサーバーを再起動してください。

各項目（読み取り専用のSQLも含む）に「接続テスト」ボタンがあります（`POST /api/v1/system-settings/test-connection`）。保存済みの値ではなく、**今その入力欄に入っている値**をテストするため、保存する前に新しいURLを確認できます。データベースは実際に`SELECT 1`を実行、Qdrantは`get_collections()`を呼び出し、Ollama（両エンドポイントとも）は`GET /api/tags`を叩きます（2つのモデル入力欄はさらに、サーバーが応答するだけでなく、指定したモデルが実際にpull済みかも確認します）。各テストは8秒でタイムアウトし、成功/失敗と応答時間を表示します。保存済みの値には一切触れず、これから保存しようとしている値だけを確認します。

## ローカルディスクへのミラーとGitHub自動保存

エピソードを保存するたびに、プレーンなMarkdownのコピーがディスクにも書き出されます（`writers_STORAGE_DIR`、作品ごとに1フォルダ、エピソードごとに1つの`.md`ファイル。ファイル名はエピソード番号とIDで決まるため、タイトルを変更してもファイルが孤立しません）。アプリが読み取るデータの正はデータベースのままで、これは書き込み専用のミラーです。アプリ外での閲覧性と、GitHub同期の元データとして機能します。

`GIT_REMOTE_URL`（Personal Access Tokenを埋め込んだgitリモートURL。例：`https://<token>@github.com/<you>/<repo>.git`）を設定すると、バックグラウンドのループがこのミラーの変更点を`GIT_AUTOSYNC_INTERVAL_SECONDS`（既定300秒）ごとにコミット・プッシュします。`GIT_REMOTE_URL`が未設定の場合、プッシュは行われずローカルディスクへのミラーのみが動作します。プッシュ・コミットの失敗（ネットワーク不通、トークン不正、リモートに拒否された等）はログに記録され、次回のタイミングで再試行されるだけで、アプリ本体の保存処理を妨げることはありません。

## バックアップとリストア

設定画面の「バックアップ」タブ（サーバー全体の機能で、特定の作品専用ではありません）：自動バックアップが有効かどうか、現在の間隔・保持件数、これまでに取得したバックアップの一覧（内容・サイズ）を確認できます。「今すぐバックアップ」を押すとその場で1回実行し、結果（成功/失敗）が表示されます。

自動バックアップは**既定で無効**です。`BACKUP_ENABLED=true`（`BACKUP_INTERVAL_SECONDS`、既定86400秒＝1日ごと。`BACKUP_RETENTION_COUNT`、既定7件。それより古いものは自動削除されます）を設定すると有効になります。実行内容は`scripts/backup.sh`を手動実行するのと同じで、PostgreSQLのダンプ（`pg_dump`）と、何か索引済みであればQdrantコレクションのスナップショットを、`BACKUP_DIR`（Docker Compose／デスクトップインストーラ構成では既定でコンテナボリューム）配下のタイムスタンプ付きフォルダに保存します。単体スクリプトと違い、Qdrant URLの解決はアプリの他の部分と同じ方法（接続設定でのライブ上書きも含む）で行われ、固定の環境変数だけには依存しません。

リストアはリポジトリルートの`scripts/restore.sh <バックアップディレクトリ>`から、`docker-compose`スタックを起動した状態のマシンで実行してください。**確認プロンプトなしで現在のデータベース内容を置き換えます**ので、実行前にパスを必ず確認してください。画面上にリストアボタンはありません。リストアは現在のデータベース内容を本質的に破壊する操作のため、意図的にコマンドライン操作のままにしています。Ollamaのモデルはこの仕組みの対象外です。必要な場合は別途`ollama pull`し直してください。ローカルディスクへのエピソードミラー（および設定していればGitHub同期）は、エピソード本文専用の別系統の常時バックアップであり、上記のバックアップ/リストアの仕組みには含まれません。

## モバイル表示
